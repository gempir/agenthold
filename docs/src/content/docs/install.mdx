title: "Install"
description: "Run agenthold on a Linux KVM host with one binary and a YAML configuration."
---

agenthold runs as a single foreground process on a Linux x86_64 or arm64 host with `/dev/kvm`. The node
needs root for the Firecracker jailer, tap devices and nftables. It serves plain HTTP; put a reverse proxy
or a tunnel that provides HTTPS in front of it. A host without KVM cannot run agents itself, but it can be
the controller for [edge nodes](/edge-nodes/) that do.

A release consists of `agenthold-linux-<arch>`, `base-<arch>.ext4.zst`, `runtime-linux-<arch>.manifest.json`
and a checksum file. `scripts/release/build.sh` produces them for the host architecture (see the
[development guide](/development/) and [guest artifacts](/guest-artifacts/)). There is no migration from the
former container-based installation.

## Configure

Choose a persistent data directory and a public HTTPS URL. Generate the one local administrator's
password hash with `agenthold hash-password`, and put the hash in a YAML file readable only by the operator:

```yaml
listen: 127.0.0.1:8080
public_url: https://agents.example.com
data_dir: /var/lib/agenthold
auth:
  local:
    username: admin
    password_hash: '$argon2id$REPLACE_WITH_GENERATED_HASH'
sandbox:
  network_pool: 10.213.0.0/16
```

Instead of a local administrator, configure [OIDC or GitHub OAuth](/auth/). With neither configured nobody
can sign in. The reverse proxy must forward WebSockets and preserve the public host and scheme; set
`public_url` to the URL users actually open. Keep the proxy and any administration ports inaccessible to
guests. See [security](/security/) and [egress](/egress/).

## Database

SQLite is the default and needs no separate service. The database file is
`<data_dir>/agenthold.db`. To choose another SQLite path or an existing PostgreSQL database, set
`database.url`:

```yaml
database:
  url: sqlite:/var/lib/agenthold/agenthold.db
```

`AGENTHOLD_DATABASE_URL` overrides this setting. PostgreSQL URLs begin with `postgres://` or
`postgresql://`; use verified TLS for a remote database. The server applies its schema migrations on
startup. See [database configuration and backups](/database/) for PostgreSQL setup and testing.

## Runtime artifacts

A release binary contains the architecture-matched Firecracker runtime, kernel and guest daemon. The shared
base disk is separate (about 780 MiB compressed, 2.4 GiB on disk). On first start the server fetches it and
verifies it against the SHA-256 sums embedded in the binary, so **the source of the bytes needs no trust**.
The verified, uncompressed base lives at `<data_dir>/base/<sha256>.ext4` (the SHA-256 of the *uncompressed*
image, `base.sha256` in the manifest), mode `0644`, in a `0700` directory owned by root. The server uses a
file that is already there without network access.

Where a missing base comes from, first match wins:

1. `sandbox.firecracker.base_url` (`AGENTHOLD_FIRECRACKER_BASE_URL`). A URL ending in `/` is the `/dl/` root
   of another agenthold, for example `https://demo.agenthold.dev/dl/`: the server then fetches
   `<root><version>/base-<arch>.ext4.zst`. Any other URL names the compressed image itself.
2. For an [edge node](/edge-nodes/): the controller it joined.
3. The URL embedded in the release, if the release has one.

```yaml
sandbox:
  firecracker:
    base_url: https://demo.agenthold.dev/dl/
```

The download resumes where it stopped: bytes accumulate in `<data_dir>/base/.<sha256>.ext4.zst.part`
(requested with `Range`/`If-Range`), transient errors are retried with backoff, and it only gives up after 30
minutes without a single new byte, so a slow uplink does not fail a healthy transfer. Progress is logged every
few seconds. Two processes sharing a data directory take turns (a lock file). After the checksum of the
compressed file is verified it is **kept** as `<data_dir>/base/<sha256>.ext4.zst`, next to the decompressed
image (another 780 MiB), so this installation can pass it on, see below.

An offline installation places the image before the first start. Either the decompressed one:

```sh
sha=$(jq -er .base.sha256 runtime-linux-arm64.manifest.json)
sudo install -d -m 0700 /var/lib/agenthold /var/lib/agenthold/base
sudo zstd -d --long=27 --sparse base-arm64.ext4.zst -o "/var/lib/agenthold/base/$sha.ext4"
echo "$sha  /var/lib/agenthold/base/$sha.ext4" | sudo sha256sum --check
sudo chown root:root "/var/lib/agenthold/base/$sha.ext4" && sudo chmod 0644 "/var/lib/agenthold/base/$sha.ext4"
```

or just the compressed file as `<data_dir>/base/<sha256>.ext4.zst` (verified against `base.compressed.sha256`
and decompressed on start; without it the server cannot hand the image to others).

The `chown` matters: `zstd` copies the owner of the compressed file onto its output. The base needs about
2.5 GiB (arm64) of free space plus the kept compressed file; every release carries its own base. A
mismatching or corrupt decompressed file stops the server at startup instead of being replaced.

### Serving the release to others

A server running a release binary serves what it runs, without authentication and read-only, under
`<public_url>/dl/`. Edge nodes use it for their base image, and another installation can point `base_url` at
it:

| Path | Content |
| --- | --- |
| `/dl/manifest.json` | index: version and, per architecture, the files below (`Cache-Control: no-cache`) |
| `/dl/<version>/agenthold-linux-<arch>` | the running binary |
| `/dl/<version>/runtime-linux-<arch>.manifest.json` | the embedded runtime manifest |
| `/dl/<version>/base-<arch>.ext4.zst` | the compressed base image |

Files are immutable per version, carry their SHA-256 as `ETag` and support `Range`, `If-Range` and `HEAD`. The
base image is only offered when `<data_dir>/base/<sha256>.ext4.zst` exists and matches the checksum in the
manifest (the startup log says whether it does, and `/dl/manifest.json` then leaves `base` out). A server that
never downloaded the image itself, for example a controller with `sandbox.driver: none`, needs that file
copied there. A client address can run two large downloads at a time; more get `429`. Behind a reverse proxy
the address comes from `X-Forwarded-For`: the proxy must **append** the real client address to that header
(the right-most public entry is used), otherwise every client shares one limit. Responses name no paths or
system errors; the reason a file is not served (for example a base image that is missing or does not match)
is in the server log.

Edge nodes are told to download from `<public_url>/dl/`. With `public_url` unset (it defaults to
`http://localhost:8080`) or pointing at loopback, no node could reach that, so the server does not
advertise it and logs a warning at startup; set `public_url` to an address the nodes can open.

To publish other versions or architectures (a build host serving its releases), put files into
`<data_dir>/dl/`, with the same layout. They are served under `/dl/` and win over the generated files of the
same name, including a `manifest.json` of your own. Files in a version directory
(`<version>/...`, for example `v0.4.0/` or `sha-<commit>/`) are served with immutable caching headers, so treat a
published version directory as immutable and publish changes under a new version; everything else
(including your `manifest.json`) is revalidated by clients on every use. A file in that directory that
cannot be opened (permissions, too many open files) is an error (`500`, logged), never replaced by the
generated file of the same name. Hidden files, directories and anything that leaves
that directory (including through symlinks) are never served. A development build (without the release
bundle) serves nothing of its own.

Point `AGENTHOLD_CONFIG` at the YAML file and run `agenthold` as root in the foreground. To install a
systemd service instead, use:

```sh
sudo agenthold install --config /etc/agenthold/agenthold.yaml
sudo systemctl enable --now agenthold
sudo journalctl -u agenthold -f
```

`install` writes the service but does not start it. The server logs startup errors, including missing KVM,
invalid configuration and failed runtime downloads.

## Back up

`agenthold backup` and `agenthold restore` support SQLite only. For PostgreSQL use your database
operator's backup and recovery process; see [database backups](/database/#backups).

For SQLite, `agenthold backup` snapshots the configured database and preserves the master key and egress
CA in an archive; it does **not** include agent disks. Stop the server before separately copying the agent disk files under
`<data_dir>/agents/`, and keep the configuration and backup archive safe. Without the master key encrypted
secrets cannot be recovered. Test restores on a separate host. `agenthold restore <archive>` restores the
server data with the server stopped; restore agent disks separately.
