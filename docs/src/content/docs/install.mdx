---
title: "Install"
description: "Run agenthold on a Linux KVM host with one binary and a YAML configuration."
---

agenthold runs as a single foreground process on a Linux x86_64 or arm64 host with `/dev/kvm`. The node
needs root for the Firecracker jailer, tap devices and nftables. It serves plain HTTP; put a reverse proxy
or a tunnel that provides HTTPS in front of it. A host without KVM cannot run agents.

Native release packaging is in progress. The instructions below describe the intended release installation;
use the [development guide](/development/) to build and test the current checkout. There is no migration
from the former container-based installation.

## Configure

Choose a persistent data directory and a public HTTPS URL. Generate the one local administrator's
password hash with `agenthold hash-password`, and put the hash in a YAML file readable only by the operator:

```yaml
listen: 127.0.0.1:8080
public_url: https://agents.example.com
data_dir: /var/lib/agenthold
auth:
  local:
    username: admin
    password_hash: '$argon2id$REPLACE_WITH_GENERATED_HASH'
sandbox:
  network_pool: 10.213.0.0/16
```

Instead of a local administrator, configure [OIDC or GitHub OAuth](/auth/). With neither configured nobody
can sign in. The reverse proxy must forward WebSockets and preserve the public host and scheme; set
`public_url` to the URL users actually open. Keep the proxy and any administration ports inaccessible to
guests. See [security](/security/) and [egress](/egress/).

## Database

SQLite is the default and needs no separate service. The database file is
`<data_dir>/agenthold.db`. To choose another SQLite path or an existing PostgreSQL database, set
`database.url`:

```yaml
database:
  url: sqlite:/var/lib/agenthold/agenthold.db
```

`AGENTHOLD_DATABASE_URL` overrides this setting. PostgreSQL URLs begin with `postgres://` or
`postgresql://`; use verified TLS for a remote database. The server applies its schema migrations on
startup. See [database configuration and backups](/database/) for PostgreSQL setup and testing.

## Runtime artifacts

A release binary contains the architecture-matched Firecracker runtime, kernel and guest daemon. The shared
base disk is a separate release asset: on first start the server fetches the pinned asset and verifies its
SHA-256. For an offline installation, place the verified base image in the data directory before starting.
Release URLs and exact offline placement will be published with the release assets.

Point `AGENTHOLD_CONFIG` at the YAML file and run `agenthold` as root in the foreground. To install a
systemd service instead, use:

```sh
sudo agenthold install --config /etc/agenthold/agenthold.yaml
sudo systemctl enable --now agenthold
sudo journalctl -u agenthold -f
```

`install` writes the service but does not start it. The server logs startup errors, including missing KVM,
invalid configuration and failed runtime downloads.

## Back up

`agenthold backup` and `agenthold restore` support SQLite only. For PostgreSQL use your database
operator's backup and recovery process; see [database backups](/database/#backups).

For SQLite, `agenthold backup` snapshots the configured database and preserves the master key and egress
CA in an archive; it does **not** include agent disks. Stop the server before separately copying the agent disk files under
`<data_dir>/agents/`, and keep the configuration and backup archive safe. Without the master key encrypted
secrets cannot be recovered. Test restores on a separate host. `agenthold restore <archive>` restores the
server data with the server stopped; restore agent disks separately.
