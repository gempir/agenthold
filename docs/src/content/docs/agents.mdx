---
title: "Agent to agent"
description: "Let agents delegate tasks to each other through the platform MCP server."
---

Agents can work together. Every session gets a platform MCP server named `agenthold` with these
tools:

| Tool | Does |
| --- | --- |
| `list_agents` | lists the other agents this agent may message, with their state |
| `send_message(agent, text)` | prompts another agent and returns at once; it works on it in its own session |
| `ask(agent, text)` | prompts another agent, waits for its turn to end and returns its final answer |
| `list_threads(include_settled?)` | lists this agent's own threads, newest activity first; the one it is in is marked `current` |
| `settle_thread(thread_id?)` | settles one of its own threads (default: the current one) |
| `unsettle_thread(thread_id)` | makes one of its own settled threads active again |

`agent` is a name or an id. Messaging a sleeping agent wakes it.

## Its own threads

An agent can [settle](/sessions/#threads-and-settling) its threads when their work is done, so they leave its
users' active list: `settle_thread()` at the end of a finished task settles the thread it is in. The thread tools
only reach the calling agent's own threads; any other id is reported as not found. A new message unsettles the
thread again. Settles and unsettles by the agent appear in its audit log with the agent's name.

## Rules

- An agent may message the agents its **owner** owns and the agents that are shared with its owner. Any other
  agent does not exist for it, not even by id. Sharing is one-way: if Alice shares an agent with Bob, Bob's
  agents can message it, but Alice's agents cannot message Bob's.
- Messages are sent in the owner's name ("agent planner (for Alice)") and appear in the target's audit log.
- Every turn has a depth: 0 when a person, a schedule or a webhook started it, and one more than the deepest turn
  the calling agent is running when an agent started it. A call that would exceed depth 4 fails with an error
  ("too many agents in a row"), which stops loops such as A asking B asking A. The server computes the depth; the
  sandbox cannot influence it.

## Linked threads

Messages from agent A go to a thread (session) on the target called "From A". It is reused while it is idle, and a second
one is opened if it is busy. The session records which agent and session started it, and the UI links back to it.

## How it works

The harness starts the platform MCP server as `/opt/agenthold/sandboxd mcp` (stdio). It talks to the sandbox's
sandboxd over a unix socket, `~/.agenthold/platform.sock`, owned by the agent user. sandboxd forwards each call over
its tunnel to the server, which identifies the calling agent by the tunnel, not by anything the sandbox says. The
per-boot token stays readable only by root.
