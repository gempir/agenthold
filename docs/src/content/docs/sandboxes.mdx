title: "Sandboxes"
description: "Every agent has a microVM with persistent system and home disks."
---

Every agent has its own Firecracker microVM. All agents use the same read-only base image, with an
individual writable system overlay and a persistent home disk mounted at `/home/agent`.

## Lifecycle

| State | Meaning |
| --- | --- |
| `creating` | The agent's disks and sandbox are being set up. |
| `starting` / `stopping` | The sandbox is starting or going to sleep. |
| `running` | The sandbox is up and its guest daemon is connected. |
| `sleeping` | The sandbox is stopped. Its disks are kept; running processes are not. |
| `rebuilding` | The system is being reset and current resources applied; the home disk is kept. |
| `destroying` | The sandbox and its disks are removed, then the agent. |
| `error` | The last operation failed. The message says why; start or reset the system to retry. |

A reset discards system changes in the writable overlay and recreates it from the shared base. Home files
and conversations survive. Resource or environment changes mark the agent as `needsRebuild` in the API;
select **Reset system** to apply them.

State is stored in the [configured database](/database/). Each operation first moves the state with a
guarded update, so concurrent requests cannot both act, and then runs in the background. On startup the controller reconciles stored
state with the node's view of its sandboxes.

## Sleep and wake

Agents sleep when nobody uses them. An agent is idle when, for its idle timeout (`idleMinutes`, default 15):

- no turn is running in any of its sessions,
- no terminal is open,
- nobody prompted it, opened a terminal or used its files, and
- the processes in its sandbox used less than 5% of a CPU core. sandboxd reports their CPU time, so a long build
  or test run keeps the agent awake.

The sleeper checks every `sandbox.idle_check_interval` (default 30s) and stops idle sandboxes. Both disks and
conversations survive; running processes do not. A prompt, terminal or Start request wakes the agent again.
The harness restores the conversation where supported (see [sessions and harnesses](/sessions/)).

While an agent runs, the API reports `lastActivityAt` and `sleepsAt`, and the UI shows when it will fall asleep.
After a server restart, the idle clock of running agents starts again.

## sandboxd and the tunnel

The guest runs `sandboxd`, which connects to the node using a per-boot token. A sandbox counts as `running`
once its daemon connects. The tunnel carries terminal, file, harness and health streams. File paths are
relative to `/home/agent`; opening a terminal wakes a sleeping agent, while file operations require it to be
running.

The fake driver runs sandboxd on the server's machine as the server's user. Use it only for development and tests.
