title: "Install"
description: "Run agenthold on a Linux KVM host with one binary and a YAML configuration."
---

agenthold runs as a single foreground process on a Linux x86_64 or arm64 host with `/dev/kvm`. The node
needs root for the Firecracker jailer, tap devices and nftables. It serves plain HTTP; put a reverse proxy
or a tunnel that provides HTTPS in front of it. A host without KVM cannot run agents itself, but it can be
the controller for [edge nodes](/edge-nodes/) that do.

A release is one static binary per architecture, `agenthold-linux-amd64` and `agenthold-linux-arm64`. It
is the server, the [edge node](/edge-nodes/) and the daemon inside every machine, and it embeds Firecracker
and the jailer. It does **not** contain the guest kernel or the base disk image: those are large,
architecture-specific **assets**, built natively on a host of each architecture and served by an operator's
host under `/dl/assets/` (see [runtime artifacts](#runtime-artifacts)). The binary names the two assets it
runs with by key, a hash of their build inputs. There is no migration from the former container-based
installation.

## Download

Official binaries are published as semver GitHub releases (`v0.1.0` and later; tags with a `-` suffix such
as `v0.2.0-rc.1` are marked as pre-releases), each containing both binaries, their runtime manifests and
`SHA256SUMS`:

```sh
v=v0.1.0
base=https://github.com/gempir/agenthold/releases/download/$v
mkdir "$v" && cd "$v"
curl -fsSLO "$base/SHA256SUMS"
for f in agenthold-linux-amd64 runtime-linux-amd64.manifest.json; do curl -fsSLO "$base/$f"; done
sha256sum --check --ignore-missing SHA256SUMS
chmod +x agenthold-linux-amd64 && ./agenthold-linux-amd64 --version   # agenthold v0.1.0 (...)
jq '{kernel, base, harnesses}' runtime-linux-amd64.manifest.json      # the asset keys it needs
```

Commits on `main` are not published as GitHub releases. For a `main` build, download the `release-amd64` or
`release-arm64` workflow artifact from a green [`ci` workflow](https://github.com/gempir/agenthold/actions/workflows/ci.yml)
run (for example `gh run download <run-id> -n release-amd64`), or build from source below.

The kernel and base image are not on GitHub. A server fetches them on first start from an asset source
(see below): set `sandbox.firecracker.assets_url` to the `/dl/` root of a host that builds or serves your
architecture's assets. The demo, `https://demo.agenthold.dev/dl/`, serves arm64 assets. For amd64 (or to be
independent of anybody else's host) build them yourself on an x86_64 or arm64 Linux host:

```sh
sudo scripts/release/build-assets.sh   # build/assets/<arch>/{kernel,base,harnesses}-<key>.{json,zst}
```

and place them as described under [runtime artifacts](#runtime-artifacts), or serve that directory as
`<root>/assets/<arch>/` from any web server you trust. To build a binary from source instead:
`make web && VERSION=v0.1.0 scripts/release/build.sh` (or `VERSION=sha-$(git rev-parse HEAD)` for a `main`
commit; output in `build/release/<arch>/`).

## Configure

Choose a persistent data directory and a public HTTPS URL. Generate the one local administrator's
password hash with `agenthold hash-password`, and put the hash in a YAML file readable only by the operator:

```yaml
listen: 127.0.0.1:8080
public_url: https://agents.example.com
data_dir: /var/lib/agenthold
auth:
  local:
    username: admin
    password_hash: '$argon2id$REPLACE_WITH_GENERATED_HASH'
sandbox:
  network_pool: 10.213.0.0/16
```

Instead of a local administrator, configure [OIDC or GitHub OAuth](/auth/). With neither configured nobody
can sign in. The reverse proxy must forward WebSockets and preserve the public host and scheme; set
`public_url` to the URL users actually open. Keep the proxy and any administration ports inaccessible to
guests. See [security](/security/) and [egress](/egress/).

## Database

SQLite is the default and needs no separate service. The database file is
`<data_dir>/agenthold.db`. To choose another SQLite path or an existing PostgreSQL database, set
`database.url`:

```yaml
database:
  url: sqlite:/var/lib/agenthold/agenthold.db
```

`AGENTHOLD_DATABASE_URL` overrides this setting. PostgreSQL URLs begin with `postgres://` or
`postgresql://`; use verified TLS for a remote database. The server applies its schema migrations on
startup. See [database configuration and backups](/database/) for PostgreSQL setup and testing.

## Runtime artifacts

A release binary extracts its Firecracker and jailer to `<data_dir>/runtime/<version>/`. The guest kernel
(about 40 MiB on amd64, 19 MiB on arm64) and the shared base disk (about 800 MiB compressed, 2.4 GiB on
disk) are assets named by the keys in the embedded runtime manifest. Each has an **asset manifest**:

```json
{"format":1,"kind":"base","arch":"arm64","key":"<32 hex>",
 "sha256":"<uncompressed>","size":2584207360,"compressed":{"sha256":"<.zst>","size":815744837}}
```

An installation keeps them in its data directory:

| Path | Content |
| --- | --- |
| `<data_dir>/assets/<arch>/<kind>-<key>.json` | the asset manifest |
| `<data_dir>/kernel/<sha256>` and `.zst` | the verified kernel and its compressed file |
| `<data_dir>/base/<sha256>.ext4` and `.zst` | the verified base image and its compressed file |

On start the server reads each manifest and checks the uncompressed file against it; a verified file needs no
network access, a mismatching one stops the server instead of being replaced. When something is missing it
is fetched from an asset source, first match wins:

1. `sandbox.firecracker.assets_url` (`AGENTHOLD_FIRECRACKER_ASSETS_URL`), the `/dl/` root of an asset
   source, ending in `/` (the former `base_url` is read as the same setting);
2. for an [edge node](/edge-nodes/): the controller it joined.

The server fetches `<root>assets/<arch>/<kind>-<key>.json` and then `<kind>-<key>.zst`, checks the
compressed file and, after decompressing, the uncompressed file against that manifest. Because the manifest
comes from the source, **the source must be one you trust** (your controller or your own host); the
checksums protect against damaged transfers, not against a malicious source.

```yaml
sandbox:
  firecracker:
    assets_url: https://agents.example.com/dl/
```

The download resumes where it stopped: bytes accumulate in `.<sha256>.ext4.zst.part` next to the file
(requested with `Range`/`If-Range`), transient errors are retried with backoff, and it only gives up after 30
minutes without a single new byte. A source that never delivers a byte is given up after about 90 seconds when
another is left (5 minutes if it is the last). Progress is logged every few seconds. Two processes sharing a
data directory take turns (a lock file). The compressed file is **kept** next to the uncompressed one, so this
installation can pass the asset on (see below).

An offline installation places the assets before the first start, for example from
`scripts/release/build-assets.sh` output:

```sh
arch=amd64; d=/var/lib/agenthold
sudo install -d -m 0700 "$d" "$d/kernel" "$d/base" && sudo install -d -m 0755 "$d/assets" "$d/assets/$arch"
for kind in kernel base; do
  key=$(jq -er ".$kind.key" runtime-linux-$arch.manifest.json)
  m=build/assets/$arch/$kind-$key.json; sha=$(jq -er .sha256 "$m")
  dest="$d/$kind/$sha"; [[ $kind == base ]] && dest="$dest.ext4"
  sudo install -m 0644 "$m" "$d/assets/$arch/"
  sudo install -m 0644 "build/assets/$arch/$kind-$key.zst" "$dest.zst"   # decompressed on first start
done
```

Placing only the manifest and the `.zst` is enough: the server verifies and decompresses it on start. Files
must be owned by root and not writable by group or others.

### Serving the release to others

A server running a release binary serves what it runs, without authentication and read-only, under
`<public_url>/dl/`. Edge nodes fetch their assets from it, and another installation can point `assets_url` at
it:

| Path | Content |
| --- | --- |
| `/dl/manifest.json` | index: version and, per architecture, the files below (`Cache-Control: no-cache`) |
| `/dl/<version>/agenthold-linux-<arch>` | the running binary |
| `/dl/<version>/runtime-linux-<arch>.manifest.json` | the embedded runtime manifest |
| `/dl/assets/<arch>/<kind>-<key>.json` | an asset manifest the data directory holds (any architecture) |
| `/dl/assets/<arch>/<kind>-<key>.zst` | its compressed file, once it matches the manifest |

Binaries and asset files carry their SHA-256 as `ETag` and support `Range`, `If-Range` and `HEAD`. An asset
is offered only while its manifest is in `<data_dir>/assets/` and its compressed file matches it (the
startup log says whether this release's kernel and base are served, and `/dl/manifest.json` leaves out what
is not). A controller with `sandbox.driver: none` never fetched assets itself and needs them placed (see
above). A client address can run two large downloads at a time; more get `429`. Behind a reverse proxy the
address comes from `X-Forwarded-For`: the proxy must **append** the real client address to that header (the
right-most public entry is used), otherwise every client shares one limit. Responses name no paths or system
errors; the reason a file is not served is in the server log.

Edge nodes are told to download from `<public_url>/dl/`. With `public_url` unset (it defaults to
`http://localhost:8080`) or pointing at loopback, no node could reach that, so the server does not
advertise it and logs a warning at startup; set `public_url` to an address the nodes can open.

To publish more (other versions, a build host's files), put files into `<data_dir>/dl/` with the same
layout. They are served under `/dl/` and win over the generated files of the same name, including a
`manifest.json` of your own. Files in a version directory (`<version>/...`, for example `v0.4.0/` or
`sha-<commit>/`) are served with immutable caching headers, so treat a published version directory as
immutable; everything else is revalidated by clients on every use. A file in that directory that cannot be
opened is an error (`500`, logged), never replaced by the generated file of the same name. Hidden files,
directories and anything that leaves that directory (including through symlinks) are never served. A
development build (without the release bundle) serves operator files and the assets its data directory holds.

Point `AGENTHOLD_CONFIG` at the YAML file and run `agenthold` as root in the foreground. To install a
systemd service instead, use:

```sh
sudo agenthold install --config /etc/agenthold/agenthold.yaml
sudo systemctl enable --now agenthold
sudo journalctl -u agenthold -f
```

`install` writes the service but does not start it. The server logs startup errors, including missing KVM,
invalid configuration and failed runtime downloads.

## Back up

`agenthold backup` and `agenthold restore` support SQLite only. For PostgreSQL use your database
operator's backup and recovery process; see [database backups](/database/#backups).

For SQLite, `agenthold backup` snapshots the configured database and preserves the master key and egress
CA in an archive; it does **not** include agent disks. Stop the server before separately copying the agent disk files under
`<data_dir>/agents/`, and keep the configuration and backup archive safe. Without the master key encrypted
secrets cannot be recovered. Test restores on a separate host. `agenthold restore <archive>` restores the
server data with the server stopped; restore agent disks separately.
