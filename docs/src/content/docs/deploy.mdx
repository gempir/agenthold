## The demo builds and deploys itself

The demo at `https://demo.agenthold.dev` runs in the Lima VM `agenthold` on `scarif.local` (arm64, `/dev/kvm`).
It tests, builds and deploys every new `main` commit on its own and is the project's arm64 asset source.
Nothing connects to the box: it polls GitHub over anonymous HTTPS, and Cloudflare Tunnel carries the
traffic. GitHub Actions runs what needs no KVM (`ci.yml`: unit tests on SQLite and PostgreSQL, lint,
generated code, web, deploy script tests and native `amd64`/`arm64` release builds uploaded as workflow
artifacts `release-amd64` and `release-arm64`). Official GitHub releases are published only for semver tags
(`release.yml`: `v0.1.0` and later, with `agenthold-linux-amd64` and `-arm64`); `main` commits are not
published as `sha-*` GitHub releases. Guest kernels, base images and harness layers are never on GitHub:
each architecture's host builds them natively and serves them under `/dl/assets/`.

Two timers do the work:

| Unit | Runs | Does |
| --- | --- | --- |
| `agenthold-build.timer` → `agenthold-build.service` | 3 minutes after the last check | `/usr/local/lib/agenthold/build-local.sh`: test a `main` commit (or tagged release), build its binary and assets, publish it into the release store |
| `agenthold-pull.timer` → `agenthold-pull.service` | every 5 minutes, and right after a publish | `/usr/local/lib/agenthold/pull.sh`: deploy the store's channel |

### Build (`build-local.sh`)

By default each run asks `https://github.com/gempir/agenthold.git` for `main`'s newest non-docs commit
(skipping commits that touch only `docs/**` or `*.md`, matching `ci.yml`) and builds the release binary
locally (`scripts/release/build.sh`, default `AGENTHOLD_BUILD_RELEASES=local` for `main` commits) as
`sha-<commit>`. To build a tagged semver release instead, pass `--tag v0.1.0`: for `v*` tags,
`AGENTHOLD_BUILD_RELEASES` defaults to GitHub Releases
(`https://github.com/gempir/agenthold/releases/download`), fetching the published binary, `SHA256SUMS` and
runtime manifest (set `AGENTHOLD_BUILD_RELEASES=local` to build the tag's binary from source, or a
`file://` directory to use a downloaded CI artifact). A release that is already in the store, already
deployed, or failed with its next attempt not yet due, is skipped. Otherwise, with at least 12 GB free on
`/`, the builder fetches the repo into its own bare clone (`/var/lib/agenthold-build/agenthold.git`, owned
by the unprivileged `agenthold-build` user), checks the commit out into a fresh worktree, verifies the
release binary's `SHA256SUMS`, version and that the kernel, base and harnesses keys it names are the ones
the source computes (`scripts/guest/{kernel,base,harnesses}-key.sh`), and runs, in this order:

1. `scripts/deploy/pull_test.sh` and `bootstrap_test.sh` (build user)
2. `make test-go`: the full race suite on SQLite, also with remote edge nodes (build user; PostgreSQL is
   covered by GitHub CI)
3. `make web` (build user), and with `AGENTHOLD_BUILD_RELEASES=local` the release binary (`scripts/release/build.sh`);
   otherwise `scripts/guest/fetch-runtime.sh` for the KVM tests
4. the guest kernel, cached in `/var/cache/agenthold-build/kernel/<kernel key>` (build user)
5. `scripts/release/build-assets.sh` (root: `mmdebstrap` for the base), which builds the base image and
   harnesses layer only when their keys changed (cached in `/var/cache/agenthold-build/root/{base,harnesses}/<key>`,
   root only, and unpacked into the worktree when the key matches) and writes the assets,
   `{kernel,base,harnesses}-<key>.{json,zst}`
6. `make test-kvm` against those assets, with the **release binary** booted as every machine's sandboxd
   (root: the jailer, taps and nftables). The KVM tests run in their own network and mount namespaces with
   temporary data and jail directories, so they do not touch the live service's taps, firewall or address pool.

Every phase is a transient systemd unit in `agenthold-build.slice` (`CPUWeight=20`, `IOWeight=20`,
`MemoryHigh=3G`, `MemoryMax=4G`, `nice 10`, idle I/O, `GOMAXPROCS=4`), so a build yields to the live
controller and its microVMs and is killed before it can starve them. The unprivileged phases see an empty
`/sys/fs/cgroup/agenthold` (the live microVMs' cgroups). Logs are in `/var/log/agenthold-build/<release>.log`
and the journal (`journalctl -u agenthold-build`); runtime and memory peak per phase are in
`/var/lib/agenthold-build/last-build.json`.

Only when everything passed is the release published into the store `/srv/agenthold/releases/`: the assets
into `assets/<arch>/` (an asset that is already there stays: its key names it; the compressed base is a hard
link to the cached one), then `<version>/` (`sha-<commit>/` or `v0.1.0/`, with binary, runtime manifest and
`SHA256SUMS`) is renamed into place, then `channel.json` (format 3: the commit, version, the sha256 of
binary, runtime manifest and `SHA256SUMS`, and the kernel's, base's and harnesses' key and asset manifest
sha256) is replaced. A failure keeps the previous
channel and records the attempt: `/srv/agenthold/failed/<release>.attempt-N.log` (N = 1 to 3), the latest one
in `<release>.log` and the count in `<release>.attempts`. The same release is retried automatically, at least 15
minutes after its last failure, until it has failed 3 times; after the third failure it is not rebuilt (a new
commit is). A release that passes on a retry is published as usual and keeps its attempt logs until they age
out, so a flaky test shows up there. Failure records older than 60 days are removed. To build now,
ignoring the record and the wait: `sudo /usr/local/lib/agenthold/build-local.sh --force`. If main moves during a build, the build
finishes and the next run picks up the newest head; commits in between are skipped.

### Deploy (`pull.sh`)

`pull.sh` reads its source from `/etc/agenthold/pull.conf`:

```ini
# a local release store (the demo) ...
source=/srv/agenthold/releases
# ... or the /dl/ root of another agenthold that deployed one
# source=https://demo.agenthold.dev/dl/
# also require free space on this mount (the Mac volume behind the Lima disk); empty to skip
host_mount=/Users/gempir/dev/agenthold
```

It reads `channel.json` and checks every file against it: `SHA256SUMS` by the channel's hash, binary and
runtime manifest by both, the binary's `--version`, the runtime manifest's kernel and base keys against the
channel's, the two asset manifests by the channel's hashes, and each compressed and uncompressed asset by its
manifest. While the current service still runs, it places the assets where the binary looks for them: the
manifests in `<data_dir>/assets/<arch>/`, the kernel at `<data_dir>/kernel/<sha256>` and the base at
`<data_dir>/base/<sha256>.ext4`, each with its compressed file next to it (`+.zst`, a hard link from a local
store). Then it switches `/opt/agenthold/current`, restarts the service and waits for `/healthz` and the
expected `/api/v1/version`. A failed or interrupted switch restores and restarts the previous release, and
nothing is pruned in that case.

With `mode=node` in `pull.conf` it deploys an [edge node](/edge-nodes/) instead: the service is
`agenthold-node.service`, and the node counts as healthy when the journal of its new invocation shows the
expected version in its start line and a connection to its controller (an unreachable controller therefore
rolls the switch back; the next run tries again).

After a healthy switch it publishes `channel.json` and `<version>/SHA256SUMS` (`sha-<commit>` for `main`, or
a semver tag such as `v0.1.0`) into `<data_dir>/dl/`. The
controller's [`/dl/`](/install/#serving-the-release-to-others) serves the binary, its runtime manifest and the
assets itself, so another host can use `source=https://demo.agenthold.dev/dl/` (of the same architecture).
Pruning follows (see [Disk usage](#disk-usage)).

`sudo /usr/local/lib/agenthold/pull.sh --check` fetches and verifies everything, including unpacking the
assets, into a temporary directory and changes nothing.

The deploy scripts and units themselves are not updated by a deploy. After changing `scripts/deploy`, install
them by hand (`install -m 0755 scripts/deploy/{pull,build-local}.sh /usr/local/lib/agenthold/`, units into
`/etc/systemd/system`, `systemctl daemon-reload`).

### Bootstrap a new host

The VM needs `jq`, `zstd`, `curl`, `nftables` and `flock` (the Lima template installs them), `/dev/kvm`,
and about 3 GiB free for the first base image. To build there as well: Go (`go.mod`'s version) in
`/usr/local/bin`, `unzip flex bison
libelf-dev libssl-dev mmdebstrap` from apt, and a system user `agenthold-build`
(`useradd --system --home-dir /var/lib/agenthold-build --create-home --shell /usr/sbin/nologin agenthold-build`).

Install the first release from a release store (a build's `/srv/agenthold/releases`) or from another host's
`/dl/` root of the same architecture:

```sh
sudo scripts/deploy/bootstrap.sh /srv/agenthold/releases   # or https://demo.agenthold.dev/dl/
```

`bootstrap.sh` runs `pull.sh --install`, which verifies the channel's release like a deploy, creates
`/opt/agenthold/releases/<release>/` (the full commit for `sha-<commit>`, or the semver tag for `v*`),
places the guest assets in the data directory and points
`/opt/agenthold/current` at it; then it installs `pull.sh`, `build-local.sh` and the units (agenthold,
agenthold-node, pull service and timer, build service, timer and slice, cloudflared) without starting or
enabling them. Then write `/etc/agenthold/agenthold.yaml` (mode `0600`) and `/etc/agenthold/pull.conf`, and
start everything:

```yaml
listen: 127.0.0.1:8080
public_url: https://demo.agenthold.dev
data_dir: /var/lib/agenthold
auth:
  providers:
    - id: github
      type: github
      name: GitHub
      client_id: ...
      client_secret: ...
      github_allowed_ids: ["9765622"]
      github_roles:
        admin: ["9765622"]   # gempir
```

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now agenthold
curl -fsS http://127.0.0.1:8080/api/v1/version   # {"version":"v0.1.0",...} or {"version":"sha-<commit>",...}
sudo systemctl enable --now agenthold-build.timer agenthold-pull.timer
```

The GitHub sign-in configuration and the tunnel token are root-only files under `/etc/agenthold`
(`agenthold.yaml`, and `cloudflared.env` containing one `TUNNEL_TOKEN=` line). The remotely managed tunnel's
public hostname (`demo.agenthold.dev`) uses the service `http://127.0.0.1:8080`; start the connector with
`sudo systemctl enable --now agenthold-cloudflared`, and stop the connector on a previous host only after
the new one shows as healthy.

To exercise a real microVM against a running server, temporarily add `test_harness: true` and an
`auth.local` admin (a throwaway password hashed with `agenthold hash-password`) in a separate config file
selected through a systemd drop-in, and run the API smoke test inside the VM:

```sh
go build -o /tmp/native ./scripts/e2e/native
go build -o /tmp/fakeagent ./internal/harness/fakeagent
AGENTHOLD_SMOKE_PASSWORD=... /tmp/native -base http://127.0.0.1:8080 -fakeagent /tmp/fakeagent
```

Back up the database, master key, CA and agent disks before upgrading. Binary rollback does not reverse
database migrations, so migrations are append-only. Rolling back past G1 (host-delivered sandboxd) leaves
machines created or reset since then unbootable until you roll forward again: their base has no sandboxd of its
own. Their disks are not touched.

## Host kernel and huge pages

The demo VM's kernel is **not held back**: it runs untrusted guests, so KVM and kernel security fixes matter more
than snapshot reuse. unattended-upgrades installs new kernels but does not reboot (`Automatic-Reboot` is off); a new
kernel runs after the next manual reboot. A memory snapshot only resumes on the host kernel it was taken on, so after
such a reboot every machine's next wake is a cold boot. That is the tested fallback, and on the demo snapshots are off
anyway (it is a nested host, see [memory snapshots](/sandboxes/#memory-snapshots)). The node sets transparent huge
pages to `always` at every start, so a reboot does not bring back 4 KiB guest memory.

KVM experiments on the box take `flock /tmp/agenthold-kvm.lock`, the lock the builder's KVM phase takes, and use
their own address pool, so they never run beside the builder's tests.

## Edge node of another architecture

The demo's amd64 edge node is `korriban` (bare-metal x86_64 Arch Linux, 16 CPUs, KVM, on the same LAN as
`scarif.local`). It runs `agenthold node` directly on the host and builds its amd64 assets itself, since the
arm64 controller cannot:

- **Build container.** `/var/lib/machines/agenthold-build` is an Ubuntu 24.04 tree (debootstrap) started by
  `systemd-nspawn@agenthold-build.service` (`machines.target`, so it starts at boot). Its
  `/etc/systemd/nspawn/agenthold-build.nspawn` boots it with the host network, all capabilities, `/dev/kvm`,
  `/dev/net/tun` and the host's `/srv/agenthold` bound in, and a disk-backed `/tmp`
  (`/var/lib/agenthold-build-tmp`: nspawn's own tmpfs is `nodev`, and the KVM tests put device nodes into
  jails there). A drop-in on the nspawn unit allows creating and using device nodes (`DeviceAllow=char-* rwm`;
  mmdebstrap and the jailer need them) and caps the container at `CPUWeight=20`, `MemoryMax=24G`. Inside it
  run the same `build-local.sh`, `agenthold-build.timer` and slice as on the demo (the slice raised to
  `MemoryMax=16G`), with `AGENTHOLD_BUILD_FOLLOW=https://demo.agenthold.dev` in a drop-in: it builds the
  commit the controller runs, not main's head, so the node always matches its controller.
- **Node.** On the host, `/etc/agenthold/node.yaml` and `agenthold-node.service` (`agenthold node`, root,
  `KillMode=process` so machines survive a restart), and `agenthold-pull.timer` with `mode=node` and
  `source=/srv/agenthold/releases` in `/etc/agenthold/pull.conf`: it deploys what the container published.
- **Network.** The node dials the controller's node port. The controller advertises
  `nodes.advertise: 192.168.178.100:8091` (scarif's LAN address), and the Lima instance forwards port 8091 to
  the LAN (`portForwards` in `~/.lima/agenthold/lima.yaml` with `hostIP: 0.0.0.0`). The controller never
  connects to the node.

An update therefore flows: a `main` commit lands → the demo builds its arm64 binary and assets locally,
tests and deploys it → korriban's builder sees the new controller version, builds its amd64 binary (or
downloads it from GitHub Releases when following a semver `v*` tag) and assets (only when their keys
changed), KVM-tests with that binary and publishes → korriban's puller switches the node.

## Disk usage

The shared base and the per-agent disks can consume substantial host storage. A sparse Lima disk reports its
full configured size to the guest while the Mac only pays for the blocks that were written, so the guest can
show tens of GiB free that the Mac does not have. Measured on the Scarif demo VM:

- One base image is about 2.4 GiB, plus about 0.8 GiB for the kept compressed file. The base is the
  operating system only (the node delivers its own binary as sandboxd at boot), so it changes only when `images/base` or the
  rootfs build changes; consecutive releases normally share it, and the builder's cache, every store version
  and the base cache hold one compressed copy through hard links. After each successful switch the puller
  prunes the base cache and keeps only the base (both files) of the new release, the base of the previous
  release (the rollback target; usually the same one) and every base that an agent's `state.json` still
  references: an agent's overlay only works with the base it was created on, and it moves to the current base
  when the agent's system is reset. If any agent state cannot be read, no base is pruned. In normal operation
  that converges to one base.
- Release directories under `/opt/agenthold/releases` are pruned to the newest three, never the current or
  previous release; versions in the local release store to the newest two plus the deployed and previous
  ones (what rollback needs; their compressed bases are hard links of one file while the base is unchanged); `<data_dir>/dl/` keeps only the deployed version. Pruning only touches
  `<sha256>.ext4[.zst]` files in `<data_dir>/base/` and `<data_dir>/harnesses/`, `<sha256>[.zst]` files in
  `<data_dir>/kernel/`, 40-hex or semver `v*` release directories and `sha-<commit>` or semver `v*`
  version directories, ignores symlinks, and logs each removal and the bytes freed. It never runs after a failed or
  rolled-back deployment. Set `PRUNE=0` in the puller's environment (`systemctl edit agenthold-pull.service`)
  to disable it.
- A build needs temporary space for its worktree (with the unpacked base image, 2.4 GiB) and the Go, Bun and
  rootfs caches. Measured on 2026-11-18: about 3 GB at the peak with the base cached (the KVM tests and the
  release output hard-link the base); 6.9 GB when both still copied it. The builder refuses to start with
  less than 12 GB free.
- A fresh agent has an 8 GiB overlay and a 10 GiB home disk as sparse files; right after boot they occupy
  only a few MiB.
- Before placing a new base the puller checks free space on the guest filesystem and on `host_mount`, the
  Mac volume that backs the VM.

Free space freed inside the guest is returned to the Mac (the Lima disk shrinks after deletion), but keep
substantial headroom on the Mac volume: it is shared with everything else on the host.

## HTTPS examples

Choose one of these approaches. Each assumes agenthold listens on `127.0.0.1:8080` and
`public_url` is `https://agents.example.com`. Configure DNS and firewall access for your own host.

### Caddy

With DNS pointing to the proxy and ports 80 and 443 available, Caddy can obtain and renew a certificate.
Its reverse proxy handles WebSocket upgrades:

```caddy
agents.example.com {
  reverse_proxy 127.0.0.1:8080
}
```

See the [Caddy reverse proxy guide](https://caddyserver.com/docs/quick-starts/reverse-proxy).

### nginx

Place the `map` inside nginx's `http` block, and provide your own certificate and key:

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
server {
    listen 443 ssl;
    server_name agents.example.com;
    ssl_certificate /etc/ssl/agents/fullchain.pem;
    ssl_certificate_key /etc/ssl/agents/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 3600s;
    }
}
```

See [nginx WebSocket proxying](https://nginx.org/en/docs/http/websocket.html). Configure certificate
renewal and HTTP-to-HTTPS redirects separately.

### Cloudflare Tunnel

Create a tunnel and its DNS route in your Cloudflare account, then configure a locally managed `cloudflared`
tunnel with its credentials file:

```yaml
tunnel: YOUR_TUNNEL_ID
credentials-file: /etc/cloudflared/YOUR_TUNNEL_ID.json
ingress:
  - hostname: agents.example.com
    service: http://127.0.0.1:8080
  - service: http_status:404
```

Run `cloudflared` as a service using that configuration. See the [Cloudflare Tunnel configuration
reference](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/local-management/configuration-file/).
