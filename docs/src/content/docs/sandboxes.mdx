Every agent has its own Firecracker microVM. All agents use the same read-only base image, with an
individual writable system overlay and a persistent home disk mounted at `/home/agent`.

## Lifecycle

| State | Meaning |
| --- | --- |
| `creating` | The agent's disks and sandbox are being set up. |
| `starting` / `stopping` | The sandbox is starting or going to sleep. |
| `running` | The sandbox is up and its guest daemon is connected. |
| `sleeping` | The sandbox is stopped. Its disks are kept, and usually its memory too (see [memory snapshots](#memory-snapshots)). |
| `rebuilding` | The system is being reset and current resources applied; the home disk is kept. |
| `destroying` | The sandbox and its disks are removed, then the agent. |
| `error` | The last operation failed. The message says why; start or reset the system to retry. |

A reset discards system changes in the writable overlay and recreates it from the shared base. Home files
and conversations survive. Resource or environment changes mark the agent as `needsRebuild` in the API;
select **Reset system** to apply them.

State is stored in the [configured database](/database/). Each operation first moves the state with a
guarded update, so concurrent requests cannot both act, and then runs in the background. On startup the controller reconciles stored
state with the node's view of its sandboxes.

## Clone and templates

**Clone** makes a new agent with a copy of an agent's system overlay and home disk, so installed tools,
checked-out repositories and caches come along. Only the owner can clone: the home disk can hold harness
credentials. The clone is created in the background (`creating`, then `sleeping`) and wakes on first use.

| Copied | Not copied |
| --- | --- |
| Harness, model, resources, idle time, permission policy | Shares |
| Attached library MCP servers, skills and secrets (the attachments; the secrets stay yours) | Sessions and their history |
| The agent's own MCP servers | Schedules and webhooks |
| System and home disks | API ids and the sandbox's network address |

- The source must be at rest while its disks are copied. A running agent is stopped, copied and started again; the
  clone is refused while a prompt is running, and no prompt is accepted while the copy is made.
- A machine with changes that need a reset (`needsRebuild`) is not cloned: a clone would inherit them unapplied.
  **Reset system** first (home files are kept), then clone. The API answers 409. The base image does not matter: a
  clone stays on its source's base (its system overlay only makes sense on that one), which stays on the node while
  any machine uses it. An [edge node](/edge-nodes/) still on a release from before host-delivered sandboxd reports
  a machine on an older base, and that clone is refused until a reset, as before (its guest boots the sandboxd
  baked into the base); run the controller's release on every node. A source that is being cloned is `stopping` until the copy is done, and
  cannot be started, stopped or cloned a second time meanwhile.
- A clone lives on the same node as its source, because disks never leave a node. If that node is offline, cloning
  fails like any other operation on it.
- Disks are copied as a reflink (instant, shared blocks) where the filesystem supports it, such as btrfs or XFS,
  and otherwise as a sparse copy that moves only the allocated data. A copy that fails or is cancelled leaves
  nothing behind.
- The clone boots as its own machine: its first boot is told, in its boot configuration, to clear the machine id,
  Docker's engine id, SSH host keys and random seeds that the copied disks carry, and sandboxd then stamps the
  system with the clone's id. Files in the home directory are copied as they are, including conversation files kept
  by the harness, which the clone does not reference.
- **In-sandbox harness logins are shared by copying.** If the agent logged in to its harness inside the sandbox
  (`credentialsInSandbox`), the credentials are on its home disk and in every clone. Providers that rotate OAuth
  refresh tokens (each refresh invalidates the previous token) then make source and clone invalidate each other.
  Prefer account-level logins (Account settings) for machines you clone or use as templates; an agent that uses
  them holds no credentials of its own.
- If the server restarts during a copy (or is shut down: a copy in flight is cancelled, not waited for), it resumes
  the clone and starts the source again if it was running. A clone that cannot be finished ends in `error`; delete it
  and clone again. Leftovers of a failed copy are removed.
- The copy keeps the source's record of what its system was built from, so `needsRebuild` stays truthful.

A **template** is a machine with `isTemplate` set: set it with **Save as template** in the agent's settings or with
`PATCH /agents/{id}`. The machine is stopped first (refused while it works on a prompt) and never started again:
it cannot be started, chatted with, scheduled or messaged by other agents, and it is listed apart from your agents
(`GET /agents` leaves templates out; `?template=true` lists only them, `?template=all` both). Its schedules and
webhooks are disabled when it becomes a template, cannot be enabled while it is one, and stay disabled when it is
converted back. **New agent** offers your templates
under "Start from"; that is a clone, and `POST /agents/{id}/clone` with `asTemplate` makes the copy a template
straight away. **Convert to agent** turns a template back into a normal machine. Templates belong to their owner;
sharing does not give anyone the right to clone them.

## Docker in a machine

A machine is a full VM with its own kernel (overlayfs, bridge, veth and nftables are built in; `/var/lib/docker`,
`/var/lib/containerd` and `/var/lib/containers` sit on the machine's disk), so Docker runs in it as on any Linux host.
Docker is not in the base image: install it once (`sudo apt-get install docker.io`) and start it as a
[service](/apps/#keeping-a-dev-server-alive), so it comes back when the machine wakes:

```
start_service(name: "docker", command: "sudo sh -c 'containerd & until [ -S /run/containerd/containerd.sock ]; do sleep 0.2; done; exec dockerd --containerd=/run/containerd/containerd.sock'")
```

(or add that command to the machine's **Services** settings). `sudo docker ...` then works; add the agent user to the
`docker` group if it should not need `sudo`.

Start containerd yourself like this, rather than running a bare `dockerd`: a `dockerd` that starts its own
containerd gives it a fixed 15 seconds to open its socket and exits with `failed to start containerd: timeout
waiting for containerd to start` if it takes longer. The first start after an install is cold (both binaries are
read from the disk and Go's start-up cost is high in a small VM) and can exceed that on a busy host. Where
containerd is started separately `dockerd` waits for it as long as it needs. Which cgroup the daemon starts in
does not matter: harnesses, terminals and services run in their own cgroup v2 leaf, and Docker works from there.

## Sleep and wake

Agents sleep when nobody uses them. An agent is idle when, for its idle timeout (`idleMinutes`, default 15):

- no turn is running in any of its sessions,
- no terminal is open,
- nobody prompted it, opened a terminal or used its files, and
- the processes in its sandbox used less than 5% of a CPU core. sandboxd reports their CPU time, so a long build
  or test run keeps the agent awake.

The sleeper checks every `sandbox.idle_check_interval` (default 30s) and puts idle sandboxes to sleep. A
prompt, terminal, Start request or [preview](/previews/) request wakes the machine again. Disks and conversations
always survive; with a [memory snapshot](#memory-snapshots) running processes do too. The harness itself is
always started anew after a wake and restores the conversation where supported (see
[sessions and harnesses](/sessions/)): no turn is running when a machine sleeps (busy machines do not idle-sleep),
and its connection to the controller ends with the sleep.

While an agent runs, the API reports `lastActivityAt` and `sleepsAt`, and the UI shows when it will fall asleep.
After a server restart, the idle clock of running agents starts again.

## What is happening right now

While a message waits for its first answer (the machine wakes, the harness starts), the chat offers **What is
happening**: a live log of the agent's last few hundred platform events. It shows the wake (resume or cold boot,
and why a snapshot could not be used), the guest's boot console (kernel, sandboxd's init phases, its tunnel
attempts), refused tunnel connections and why, the harness start with timings (process, ACP `initialize`,
`session/new` or `session/resume`, the prompt and its first update), and the harness's stderr. A failed turn
offers the same log as **Show what happened**. The API is `GET /api/v1/agents/{id}/activity?after=<seq>`. The log
lives in the controller's memory: it is empty after a restart, and an edge node's guest console is not in it.

## Memory snapshots

Sleep pauses the microVM and writes a Firecracker snapshot of it (its device state and its memory) next to its
disks; wake starts a new microVM from that snapshot and resumes it. What survives a sleep:

- every process, with its memory: services, background jobs, shells in `tmux`, files in `/dev/shm` and `/tmp`;
- the guest's wall clock is wrong after a resume (it continued from the moment of the snapshot): the node sends
  the current time with the wake, and sandboxd steps the clock before anything else;
- TCP connections to the outside are broken (the remote ends gave up long ago): clients must reconnect;
- terminals and the harness are not kept: they end with the sleep, like a disconnect.

A wake from a snapshot takes about half a second until sandboxd is connected, and its services answer right
away instead of starting up.

**Not on a nested host.** Snapshots are off by default when the node itself runs in a virtual machine (Lima,
a cloud VM, the demo box). A resumed guest's memory is mapped from the snapshot file, which gets no huge pages:
every page the guest touches again is a 4 KiB fault, and under nested virtualization each fault is an exit to
the outer hypervisor. Measured on the demo box (4 GiB guest): allocating 1 GiB took 0.4 s after a cold boot and
17 to 150 s after a resume, and a resumed Claude Code needed 111 s to start. A cold boot there reaches sandboxd
in about 0.4 s. Set `snapshots: true` to use them anyway.

**Huge pages.** The node switches the host's transparent huge pages to `always` at start (Firecracker does not
mark guest memory for them, so the common `madvise` mode leaves guest RAM in 4 KiB pages). On the demo box this
took a 4 GiB guest's boot from 25 s to 0.13 s until init. `transparent_hugepages: keep` leaves the host setting.

**Cold boot fallback.** Anything unexpected makes the wake a normal boot from the disks, which are then as a
power cut left them (sandboxd flushed them before the snapshot was taken, and the journal is replayed):

- the machine has no snapshot (it was stopped some other way), or its files are missing or incomplete;
- Firecracker, the guest kernel, sandboxd, the host kernel or the host CPU model changed since the snapshot (a
  snapshot only resumes on the same software and hardware, see Firecracker's
  [snapshot support](https://github.com/firecracker-microvm/firecracker/blob/v1.18.0/docs/snapshotting/snapshot-support.md));
  so the first wake after an upgrade that changes one of them is a boot;
- the machine's size, base image or disks changed since the snapshot;
- Firecracker refuses to load the snapshot, the resumed guest does not answer the node, or it does not
  reconnect its tunnel within 15 seconds.

A snapshot is used once: it is invalidated before the resumed machine runs. Sleep falls back to a shutdown when
the guest's sandboxd is too old to resume (machines booted by an older release: after their next boot they can),
when the snapshot does not fit (see below) or when taking it fails; the machine then simply boots at its next wake.

**Disk.** Each sleeping machine keeps one snapshot in `<data_dir>/agents/<id>/snapshot/`. The memory file has the
size of the guest's memory but is sparse: before the snapshot a balloon device takes the guest's free memory, and
the pages that are zero (all of the balloon's, and memory the guest never used) are not stored. A machine that
used little memory takes about 100 MiB on disk; one that had 400 MiB of freed memory takes about 110 MiB with the
balloon and 490 MiB without. While a resumed machine runs, its memory file stays on disk (Firecracker maps the
guest's memory from it) until the machine sleeps again or stops. Snapshots are deleted with their machine and by
Reset system; a clone copies the disks only, never the memory.

The cap and the reserve are checked conservatively: a sleep asks for the guest's full memory size (Firecracker
writes the file fully before the zero pages are removed, so that much must be free for a moment), and the node's
total counts the memory files of resumed machines too, including the one the new snapshot replaces.

Firecracker writes the snapshot into `<id>/snapout/`, the only snapshot directory its (jailed, unprivileged) user
can write. The node takes the files from there without following links, checks them, and moves them into
`<id>/snapshot/`, which belongs to root and is attached to a resumed VM read-only. A sleep takes seconds; other
machines on the node are not held up meanwhile.

**Configuration** (`sandbox.firecracker`):

| Key | Default | Meaning |
| --- | --- | --- |
| `snapshots` | `true`, `false` on a nested host | `false`: sleep is a shutdown and wake a boot. |
| `transparent_hugepages` | `always` | `keep`: do not switch the host's transparent huge pages to `always`. |
| `snapshot_max_gb` | `0` (no cap) | Disk space all snapshots of this node may take. A sleep that would exceed it is a shutdown. |
| `snapshot_reserve_gb` | `2` | Free space a snapshot must leave on the data filesystem. |
| `balloon` | `true` | Shrink snapshots with a virtio balloon (adds 0.2 to 1.5 s to a sleep, up to about 2 s for a 2 GiB machine with much freed memory). With it, the guest also reports the memory it frees to the host (free page reporting). Takes effect at a machine's next boot. |

Each node decides on its own: an [edge node](/edge-nodes/) uses its own configuration, and the controller only
sees sleep and wake as before.

## sandboxd and the tunnel

The guest runs `sandboxd`, which connects to the node using a per-boot token. A sandbox counts as `running`
once its daemon connects. The tunnel carries terminal, file, harness and health streams. File paths are
relative to `/home/agent`; opening a terminal wakes a sleeping agent, while file operations require it to be
running.

`sandboxd` is not part of the base image: the node hands its own sandboxd to every guest at boot (as the
initramfs, see [Guest artifacts](/guest-artifacts/#boot-contract)). A machine therefore gets a new release's
sandboxd, and the features that need it, at its next start: a running machine keeps the one it booted with, and a
sleeping machine's memory snapshot is not resumed by a node whose sandboxd differs (that wake is a boot). The node logs a machine that still runs an older sandboxd, and features it lacks say
"restart the machine to update it". Reset system is never needed for that.

The fake driver runs sandboxd on the server's machine as the server's user. Use it only for development and tests.
