Automatic demo publication and the Scarif pull timer are **disabled** until the bundled server and initial
deployment are validated. Pushing to `main` does not deploy a server while they are disabled.

## Pull deployment for the demo

The prepared design uses outbound HTTPS from the Linux Lima VM on `scarif.local`; GitHub does not connect to
the Mac and no deployment credentials leave the host. The publication workflow builds an arm64 binary and
matching base after a successful main CI run. It publishes immutable `sha-<commit>` release assets and
updates a small `demo-main/channel.json` pointer only while that commit is still the main head. Manual
workflow runs are subject to the same checks. The automatic `workflow_run` trigger remains commented out.

The disabled `agenthold-pull.timer` runs `agenthold-pull.service`, which reads the channel, checks the GitHub
main head and verifies the binary and runtime manifest SHA-256 values. It downloads the compressed base while
the current service runs, checks both the compressed and uncompressed hashes, and unpacks it once to the
content-addressed base cache. It rechecks main before switching `/opt/agenthold/current`, then restarts the
service and checks both health and the expected version. A failed or interrupted switch restores and restarts
the previous release. Previous base disks remain available for rollback.

The updater refuses to bootstrap an empty installation. The first release is installed by hand, validated,
and only then handed over to the timer.

### Bootstrap the first release

The VM needs `jq`, `zstd`, `curl`, `nftables` and `flock` (the Lima template installs them), `/dev/kvm`, and
about 3 GiB free for the first base image. Build a `sha-<commit>` release (the pull channel only accepts
full-commit versions), copy `build/release/arm64` and `scripts/deploy` into the VM and run the bootstrap:

```sh
# On the Mac or any Linux arm64 host with the repository checked out; make web first.
VERSION=sha-$(git rev-parse HEAD) scripts/release/build.sh
# Inside the demo VM, as root:
scripts/deploy/bootstrap.sh /path/to/arm64
```

`bootstrap.sh` verifies the checksums, creates `/opt/agenthold/releases/<full-commit>/`, points
`/opt/agenthold/current` at it, unpacks and verifies the base into `/var/lib/agenthold/base/<sha256>.ext4`
and installs `pull.sh` and the four units (agenthold, pull service and timer, cloudflared) without starting
or enabling them. Then write `/etc/agenthold/agenthold.yaml` (mode `0600`) and start the service:

```yaml
listen: 127.0.0.1:8080
public_url: https://demo.agenthold.dev
data_dir: /var/lib/agenthold
auth:
  providers:
    - id: github
      type: github
      name: GitHub
      client_id: ...
      client_secret: ...
      github_allowed_ids: ["9765622"]
```

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now agenthold
curl -fsS http://127.0.0.1:8080/healthz
curl -fsS http://127.0.0.1:8080/api/v1/version   # {"version":"sha-<commit>",...}
```

To exercise a real microVM before publishing, temporarily add `test_harness: true` and an `auth.local` admin
(a throwaway password hashed with `agenthold hash-password`) in a separate config file selected through a
systemd drop-in, and run the repository's API smoke test inside the VM against `http://127.0.0.1:8080`:

```sh
go build -o /tmp/native ./scripts/e2e/native
go build -o /tmp/fakeagent ./internal/harness/fakeagent
AGENTHOLD_SMOKE_PASSWORD=... /tmp/native -base http://127.0.0.1:8080 -fakeagent /tmp/fakeagent
```

It creates an agent, boots its microVM, uses the terminal and file API, chats with the scripted harness,
sleeps and wakes it, resets its system and deletes it. Remove the drop-in, the extra config and its password
afterwards, and start with a fresh database if the test admin should not remain.

### Hand over to the timer and publish

Only after the initial validation and explicit approval should the timer be enabled:

```sh
sudo systemctl enable --now agenthold-pull.timer
sudo systemctl status agenthold-pull.timer
sudo journalctl -u agenthold-pull.service -f
```

The GitHub sign-in configuration and the tunnel token are root-only files under `/etc/agenthold`
(`agenthold.yaml`, and `cloudflared.env` containing one `TUNNEL_TOKEN=` line); the token is not stored in the
workflow. Switching the public demo to the new VM:

1. In the Cloudflare dashboard, check that the remotely managed tunnel's public hostname
   (`demo.agenthold.dev`) uses the service `http://127.0.0.1:8080`. That address is local to whichever host runs
   the connector, so it routes correctly on the new VM.
2. Start the connector in the VM: `sudo systemctl enable --now agenthold-cloudflared`.
3. Stop the old connector on the previous host *after* the new one shows as healthy in the dashboard. Do not
   leave both connectors running unless the origin routes correctly on both hosts.
4. Enable the pull timer as above.

Back up the database, master key, CA and agent disks before upgrading. Binary rollback does not reverse database
migrations.

## Disk usage

The shared base and the per-agent disks can consume substantial host storage. A sparse Lima disk reports its
full configured size to the guest while the Mac only pays for the blocks that were written, so the guest can
show tens of GiB free that the Mac does not have. Measured on the Scarif demo VM:

- One base image is about 2.4 GiB. The embedded guest daemon differs per release, so every deployed commit
  brings a new base, and the puller keeps the old ones for rollback and for agents that have not been reset
  yet. Plan for about 2.4 GiB per deployed commit under `<data_dir>/base/` and prune bases that no agent uses
  by hand; nothing removes them automatically.
- A fresh agent has an 8 GiB overlay and a 10 GiB home disk as sparse files; right after boot they occupy
  only a few MiB. The limits are what an agent can grow to, 18 GiB at most with the defaults.
- Before downloading a new base the puller checks free space on the guest filesystem and, through the shared
  checkout mount (`AGENTHOLD_DEPLOY_HOST_MOUNT`, default `/Users/gempir/dev/agenthold`), on the Mac volume
  that backs the VM. `df` on the Mac and on that mount report the APFS container's free space, which also
  changes with other workloads on the Mac.

Free space freed inside the guest is returned to the Mac (the Lima disk shrinks after deletion), but keep
substantial headroom on the Mac volume: it is shared with everything else on the host.
## HTTPS examples

Choose one of these approaches. Each assumes agenthold listens on `127.0.0.1:8080` and
`public_url` is `https://agents.example.com`. Configure DNS and firewall access for your own host.

### Caddy

With DNS pointing to the proxy and ports 80 and 443 available, Caddy can obtain and renew a certificate.
Its reverse proxy handles WebSocket upgrades:

```caddy
agents.example.com {
  reverse_proxy 127.0.0.1:8080
}
```

See the [Caddy reverse proxy guide](https://caddyserver.com/docs/quick-starts/reverse-proxy).

### nginx

Place the `map` inside nginx's `http` block, and provide your own certificate and key:

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
server {
    listen 443 ssl;
    server_name agents.example.com;
    ssl_certificate /etc/ssl/agents/fullchain.pem;
    ssl_certificate_key /etc/ssl/agents/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 3600s;
    }
}
```

See [nginx WebSocket proxying](https://nginx.org/en/docs/http/websocket.html). Configure certificate
renewal and HTTP-to-HTTPS redirects separately.

### Cloudflare Tunnel

Create a tunnel and its DNS route in your Cloudflare account, then configure a locally managed `cloudflared`
tunnel with its credentials file:

```yaml
tunnel: YOUR_TUNNEL_ID
credentials-file: /etc/cloudflared/YOUR_TUNNEL_ID.json
ingress:
  - hostname: agents.example.com
    service: http://127.0.0.1:8080
  - service: http_status:404
```

Run `cloudflared` as a service using that configuration. See the [Cloudflare Tunnel configuration
reference](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/local-management/configuration-file/).
