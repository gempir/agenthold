agenthold does not implement an agent loop. A **harness** (Claude Code, ...) runs inside each sandbox and speaks
the [Agent Client Protocol](https://agentclientprotocol.com) (ACP) on stdio. The server is the ACP client.

## How a turn works

1. A user prompts a session (the agent's owner or a user it is shared with). If the agent sleeps, the prompt wakes it.
2. The server makes sure the agent's harness is running. sandboxd starts it as the `agent` user, in
   `/home/agent`, with the sandbox's environment plus what the adapter adds. Its stdio goes over the tunnel.
   One harness process serves all of an agent's sessions.
3. If the harness doesn't know the session yet (new process after a sleep or restart), the server uses
   `session/load` when the harness supports it, and `session/resume` otherwise. History the harness replays
   while loading is not stored again. Without either capability, a new ACP session starts and the log records a
   notice that the context was reset.
4. `session/prompt` runs. Every `session/update` the harness sends is appended to the session's event log and
   streamed to everyone watching.

The client file system and terminal capabilities are not advertised. The harness uses its own tools inside
its sandbox.

## Event log and streaming

Each session has an append-only log of events, each with a sequence number. Event types are `prompt`, `update`
(an ACP `SessionUpdate`, stored as received), `permission`, `permission_resolved`, `turn_end`, `error` and
`notice`. The stream (`GET /api/v1/sessions/{id}/stream?after=<seq>`, WebSocket) sends every stored event after
the cursor and then live events, with no gap or duplicate between the two. A browser that reloads mid-turn
reconnects with the last sequence number it saw and continues. `GET /sessions/{id}/events` returns the same log
as JSON.

## Permissions

Each agent has a permission policy:

- `auto-approve` (default): the sandbox is the safety boundary. Requests are approved with the harness's
  one-time "allow" option and logged as auto-approved.
- `ask`: everyone connected with access sees the request with the harness's options. The turn waits until someone answers
  or cancels.

## Signing in a harness

### Account logins (the normal way)

Claude Code and Codex logins live on your account, under **Provider logins** (`/settings/providers`). Connect
each once; every agent that uses your logins then has them when its harness starts, and switching an agent between
Claude Code and Codex needs no new sign-in.

| Harness | What you connect | How the harness gets it | Refresh |
| --- | --- | --- | --- |
| Claude Code | **Subscription:** the token `claude setup-token` prints (Claude Pro/Max, valid for a year) | `CLAUDE_CODE_OAUTH_TOKEN` holds a placeholder; the proxy puts the token into the `Authorization` header of requests to `api.anthropic.com` | none needed |
| Claude Code | **API key** | `ANTHROPIC_API_KEY` placeholder, swapped in `x-api-key` | none |
| Codex | **ChatGPT login:** the `auth.json` that `codex login` writes (run it with a temporary `CODEX_HOME`, the page shows the command) | `~/.codex/auth.json` with placeholder tokens; the proxy puts the access token into requests to `chatgpt.com/backend-api/` | by the server, see below |
| Codex | **ChatGPT access token** (`at-…`, if your ChatGPT workspace issues them) | `CODEX_ACCESS_TOKEN` placeholder, swapped for `auth.openai.com` (whoami only) and `chatgpt.com/backend-api/` | none |
| Codex | **API key** | `OPENAI_API_KEY` placeholder (and an `auth.json` naming it), swapped for `api.openai.com` | none |

The real values are encrypted at rest with the master key, never returned by the API and never enter the
sandbox. The proxy replaces a placeholder only inside the one header the harness sends it in, only for the hosts
(and paths) above. Agents using account logins are therefore not marked "credentials inside sandbox".

**Refresh.** A ChatGPT login has a short-lived access token and a refresh token that changes on every refresh
(reusing an old one fails). If every sandbox refreshed on its own, the first would log all the others out. So the
server is the only place that refreshes: it renews the access token an hour before it expires (checked every five
minutes) and stores the new refresh token. Sandboxes get an access-token placeholder shaped like a JWT that never
expires, so Codex does not refresh by itself; if it still tries (after a 401), the proxy answers its request to
`auth.openai.com/oauth/token` locally: the server refreshes, at most once a minute however many sandboxes ask, and
replies with the same placeholders. Connecting a ChatGPT login refreshes it once at once, which checks it and
takes it over: Codex on the computer you copied it from would have to sign in again, which is why the page
suggests a temporary `CODEX_HOME`. If the provider rejects the refresh token, the login is marked
**connect again** on the settings page and the agent's overview.

**Whose login.** Each agent uses the account logins of one user, shown on its **Overview**: by default whoever
created it. Only you can make an agent use your logins (**Use my logins**), and only for agents you own.
Everyone who can prompt that agent (users it is shared with, schedules, webhooks, other agents) then uses your
login through it, which is why the choice is explicit and visible. You can stop it at any time (**Stop using**),
also from the settings page, which lists the agents using your logins. Your login is only delivered while you can
still see the agent. An API key secret
attached to the agent for its harness (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`) takes precedence over the account
login.

Connecting, disconnecting and refresh failures are recorded in your account's audit entries; using a
login (once per harness start), attaching and detaching it are recorded on the agent.

Changes take effect without a system reset: the proxy picks them up within seconds, and the harness restarts with the
new login once its running turns have finished.

### API keys as secrets

API keys can also go through the egress proxy as ordinary secrets: create a secret (for example the Anthropic
preset), attach it to the agent with an environment variable (`ANTHROPIC_API_KEY`), and reset the system. The sandbox only
ever sees a placeholder.

### Signing in inside one sandbox

The per-agent sign-in is a secondary override, under **Overview → Sign in inside this sandbox instead**. The server
starts the harness, reads the login methods it advertises in `initialize`, and runs the chosen method in the agent's
web terminal (for Claude Code `claude /login`). The harness stores the resulting token on the agent's home volume,
so it survives sleep and system resets. Such agents are marked "credentials inside sandbox", because the agent can read
its own login. A connected account login takes precedence over it (for Codex, a ChatGPT login delivered from the
account replaces `~/.codex/auth.json`; the previous file is kept as `auth.json.agenthold-backup`). Agents that were
signed in this way before account logins existed keep their sandbox login: they do not use anyone's account logins
until their owner chooses **Use my logins**.

## Harness adapters

An adapter (`internal/harness/<name>`) is one `harness.Adapter` value: how to start the harness in ACP mode, the npm
package of `images/base/package.json` that installs it, which environment it needs (never secret values), which
secret presets fit it, where it keeps logins and skills, terminal commands for login methods the harness advertises
without one, and login methods the server may call on its own when the harness asks for authentication (such as an
API key provided as a secret). Harnesses whose login can live on the account set `Login`, an `AccountLoginer` (what
can be connected, how it is validated, and how it reaches the harness as placeholders, files and proxy injections),
which also implements `Refresher` for expiring logins. Nothing outside `internal/harness` knows about a particular
harness. Versions are pinned in `images/base/package.json` only; a test checks it against the adapters.

| Harness | ACP entry point | In the base image |
| --- | --- | --- |
| `claude-code` | `claude-agent-acp` ([@agentclientprotocol/claude-agent-acp](https://www.npmjs.com/package/@agentclientprotocol/claude-agent-acp), which bundles the Claude Agent SDK and Claude Code) | yes |
| `opencode` | `opencode acp` (native ACP, [opencode-ai](https://www.npmjs.com/package/opencode-ai)) | yes |
| `codex` | `codex-acp` ([@agentclientprotocol/codex-acp](https://www.npmjs.com/package/@agentclientprotocol/codex-acp)) | yes |
| `fake` | `/opt/agenthold/fakeagent`, a scripted agent for tests and UI work (development only) | shipped with sandboxd |

### When a harness fails

Every turn ends with a `turn_end` event, and the session is idle again before it is sent. When the harness fails, an
`error` event before it says what happened and the turn ends with `stopReason: "error"`; the next message starts a
fresh harness process and restores the conversation with `session/load` where the harness supports it.

| What happens | What the session shows |
| --- | --- |
| The harness binary is missing or exits (any code, including at startup) | that it could not run or exited with code N, with the end of its stderr |
| It is killed by something else (signal 9, usually the guest's OOM killer) | that it was killed and may have run out of memory |
| sandboxd stops it (it closed its stdout but kept running) | that the sandbox stopped it, and why |
| A setup request (`initialize`, `authenticate`, `session/new`, `session/resume`) shows no activity (ACP messages or stderr) for 2 minutes, or takes over 15 | which request timed out; the harness is stopped |
| `session/load` fails or times out | a notice that the conversation could not be restored; the turn continues in a fresh session |
| It asks for a login | auto-authentication is tried first (API key methods), then a hint to connect a login |
| It writes output that is not ACP, or a line over 10 MB | that it stopped speaking ACP; the process is stopped |
| The sandbox does not start (10 minutes) or does not open the harness stream (2 minutes) | which one |
| The tunnel drops, the sandbox stops, or the server shuts down during a turn | which one; the harness is stopped with the stream |
| The server crashed during a turn | on the next start: that the server restarted during the turn |

A cancel before the prompt reached the harness ends the turn right away; afterwards the harness gets
`session/cancel`, and if it has not ended the turn 15 seconds later the turn ends without it. Both end with
`stopReason: "cancelled"`. Permission requests that arrive after a cancel are answered "cancelled". A turn has no time
limit of its own.

One harness process serves all sessions of an agent. When it stops answering one session's request (a setup timeout,
or a cancel it ignores) while other sessions have turns running, only that session's turn ends; the process keeps
serving the others and is restarted once none uses it.

In the microVM every harness runs in a cgroup of its own, and sandboxd kills the cgroup when the harness stream ends, so
nothing the harness started outlives it, including processes that left its process group with `setsid`. Processes
started in a terminal are not affected. A process that must outlive the harness can move itself to the root cgroup
(`echo $$ | sudo tee /sys/fs/cgroup/cgroup.procs`). Outside a microVM (the fake driver) sandboxd kills the harness's
process group instead.

Signing in:

- **Claude Code:** an account login (subscription token from `claude setup-token`, or an API key), an Anthropic
  API key secret as `ANTHROPIC_API_KEY`, or `claude /login` in the agent's terminal.
- **OpenCode:** works without a login with OpenCode's free models. `opencode auth login` in the terminal, or
  provider API keys as secrets (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `OPENROUTER_API_KEY`). The model is
  `provider/model`, for example `anthropic/claude-sonnet-5-5`.
- **Codex:** an account login (ChatGPT login, ChatGPT access token or API key), or an OpenAI API key secret as
  `OPENAI_API_KEY`; the server then signs in with the key on its own.
- **OpenCode** has no account logins: it supports many providers with its own login file, which does not fit one
  login per harness. Use secrets or its terminal login.

## Base image

`images/base` (`make guest-base`) is Debian trixie with Node.js 24, the Claude Code and Codex ACP adapters, OpenCode, git, Python 3,
build tools, ripgrep, jq and headless Chromium (`CHROME_BIN`, Playwright and Puppeteer variables set). The
`agent` user has passwordless sudo inside its own sandbox.

## Testing

Use `make test` for the Go and web suites and `make test-kvm` on a KVM host. The scripted fake harness
is available for development and tests; it is not included in the production guest image.
