---
title: "Security"
description: "The trust model and boundaries around agents and credentials."
---

Agents execute code and may encounter hostile prompts or content. Users authenticate and can access only
agents they own or that have been shared with them. The host, its operator and any node are trusted: the
node runs as root and holds decrypted secrets in memory for the agents it hosts.

Each agent runs in a Firecracker microVM with a separate guest kernel and disks. The jailer constrains the
VMM, and host nftables rules direct guest traffic through the egress proxy and DNS forwarder while blocking
access to other guests and unrelated host services. A fresh boot token authenticates the guest tunnel. Treat
KVM, Firecracker, the host kernel and the node as part of the trusted computing base; isolation is not a
promise that vulnerabilities cannot occur. See [host hardening](/hardening/) and [sandboxes](/sandboxes/).

Secret values are encrypted at rest and delivered to the node's proxy, which injects them only for configured
destinations. Sandboxes receive placeholders. A destination that echoes requests can reveal an injected
secret, and account credentials explicitly saved through a terminal remain readable inside that sandbox.
See [egress and secrets](/egress/).

All agents can reach public internet destinations. An agent can exfiltrate data it can read, and prompt
injection can cause it to act on hostile content. The system does not prevent either. Share agents and
provider logins only with users you trust to use them.

The server uses OIDC, GitHub OAuth or one local administrator; owners control configuration and sharing,
while shared users can use the agent. API tokens inherit their user's permissions. Session cookies and
WebSocket origin checks protect browser sessions. Put the plain HTTP service behind an HTTPS reverse proxy
or tunnel and consider rate limits at that boundary.

Report vulnerabilities privately through the repository's GitHub security advisories.
